Section 01 · The Scenario

What you're building, and how you'll judge it

A controlled connect: one synthetic CRM, two live systems, one agent. You'll put the same 20-lead dataset into Notion and Airtable, wire Claude Desktop to both over MCP, and then ask the kinds of questions a sales lead asks every week — which deals are stuck, summarise the notes for one client, draft a follow-up plan. The point isn't the answer; it's that the answer comes from live records you can verify, not from anything you pasted into the chat.

You'll connect both systems to the Claude Desktop app, ask a shared set of natural-language questions, and then check every answer against the raw data. When the answer matches the records, you've felt what MCP does; when it doesn't, you've found exactly where an agent needs guardrails. That verification loop — ask, then compare — is the whole exercise.

The two systems you'll connect

The same CRM lives in both tools, split the way a real team splits it. Connecting both is deliberate: it lets you ask questions that only make sense when the agent can reach across systems.

Notion

The notes. A database of the 20 leads where each record carries the qualitative story — the call notes, the blockers, who the real decision-maker is. This is where "summarise the notes for Client X" gets answered.

Airtable

The numbers. The same 20 leads as a base with deal stage, value, probability, owner and next-step dates. This is where "which deals are stuck" and "what's my pipeline worth" get answered.

Claude Desktop

The agent. Once both connectors are added, Claude can read the workspace and the base directly — no exports, no pasting. You ask; it goes and looks.

How you'll judge each answer — three checks

After each question, don't just read the answer — test it. Every answer earns a yes/no on three checks, each backed by one line pointing at the record. These separate an answer that sounds right from one that is right.

A

Accuracy

"Take one fact from the answer. Open the record. Does it match — exactly?"

In plain language

Accuracy is whether every figure and claim in the answer traces back to a real record. A deal value, a stage, an owner name, a due date — each should be checkable against Airtable or Notion. If a number appears that isn't in the data, the agent invented it, and that's the single most important thing to catch.

InaccurateStates a pipeline total that doesn't add up, or names an owner the record doesn't list, or rounds a value "helpfully."
AccurateEvery value, stage and name matches the source record when you open it.

Scoring anchors

  • 1Contains a figure or claim not found in either system.
  • 3Mostly right, but one value or name is off.
  • 5Every fact checks out against the record.
Evidence to write downThe one fact you spot-checked, and the record you checked it against.
C

Completeness

"Did it use both systems when it should have — or answer from only half the picture?"

In plain language

Completeness is whether the answer draws on all the data the question needs. "Which deals are stuck?" needs the stages from Airtable and the blocker notes from Notion. An answer built from one tool alone may be accurate as far as it goes and still miss half the story.

PartialLists Negotiation-stage deals from Airtable but ignores the notes explaining why they're stuck.
CompleteCross-references stage, dates and the note to say which deals are stuck and what's blocking each.

Scoring anchors

  • 1Answers from one system when the question needs both.
  • 3Uses both but misses records that fit the ask.
  • 5Pulls every relevant record from both systems.
Evidence to write downAny record you know fits the question that the answer left out.
T

Traceability

"Can you get from a line in the answer back to the exact record it came from?"

In plain language

Traceability is whether the answer tells you where each claim came from — a company name, a lead ID, a field. An agent you can trust makes its sources findable, so verifying takes seconds, not a full re-audit. This is what makes the "compare" step fast enough to actually do.

OpaqueA confident summary with no company names or IDs — you can't check it without re-reading everything.
TraceableEach point names the deal (or lead ID) it rests on, so you can open that one record and confirm.

Scoring anchors

  • 1No sources; unverifiable without redoing the work.
  • 3Some points sourced, others floating.
  • 5Every claim ties to a named record you can open.
Evidence to write downHow long it took to verify one claim. Under 20 seconds is the goal.
Section 02 · Claude MCP

MCP is the USB port for agents

Before you connect anything, get the one idea that makes the rest obvious. MCP — the Model Context Protocol — is a standard plug. It lets an agent reach a live business system the same way a USB port lets a laptop reach any device: one shape of socket, and everything that speaks it just works.

The USB port, not the cable soup

One standard plug for many systems

Before USB, every device needed its own port and its own driver. MCP does for agents what USB did for hardware: instead of a bespoke integration per tool, there's one protocol. Claude speaks MCP; a connector is the cable; Notion and Airtable are the devices on the other end. Plug them in and the agent can read them — no custom code per system.

The one ideaYou don't teach Claude about Notion or Airtable. You give it a connector, and because both sides speak the same protocol, it can read the live system as it stands right now.

What happens when you ask

Question → connector → live system → grounded answer

When you ask "which deals are stuck?", Claude doesn't answer from memory. It uses the connector to query the live base and workspace, pulls the matching records, and builds the answer from what's actually there. Change a stage in Airtable and ask again — the answer changes too. That's the difference between an agent that reaches your systems and one that only ever saw a snapshot.

Without MCPYou export a CSV, paste it into the chat, and the agent reasons over a frozen copy that's stale the moment a teammate updates a deal.
With MCPThe agent queries the live workspace and base each time you ask, so the answer reflects the data as it is right now.

Why this is the unlock

Agents become useful when they can reach live systems

A chatbot that only knows what you type is a clever notepad. An agent that can reach the systems your business runs on — its CRM, its docs, its tickets — can answer questions about the real state of the work. MCP is the piece that turns the first into the second. Today's CRM is the example; the same plug reaches your calendar, your codebase, your data warehouse.

Keep it in viewConnectors read (and sometimes write to) real systems. That power is exactly why the verify-against-the-record habit you practise in Step 4 matters — trust, but check.

STEP 4

Compare every answer against the raw data

This is the point of the session — ask, then verify against the record

For each answer, run the three checks from Section 1 — Accuracy, Completeness, Traceability. Open the actual record in Airtable or Notion and confirm the claim. In teams, split it: one person drives Claude, another verifies against the source.

  • Spot-check a number. Take one deal value or pipeline total from the answer and confirm it against Airtable.
  • Spot-check a name. Confirm the owner or contact the answer names matches the record.
  • Look for the missing record. Is there a deal you know fits the question that the answer left out?
  • Time the trace. Pick one claim and see how fast you can get from the answer back to the source record.

Section 04 · Debrief

MCP as the USB port for your business systems

Pull back from the CRM. The dataset was a stand-in; the mechanism is the point. An agent that speaks a standard protocol can reach any system that speaks it back — and that changes what "asking a question" means at work.

The one line to take away: MCP is the standard plug that lets an agent reach live business systems. Today it was Notion and Airtable holding a CRM. Swap the devices and it's your calendar, your ticket queue, your data warehouse — same socket, same ask-in-plain-English, same verify-the-record discipline.

The connection was the easy part

Six questions worth more than the demo

Answer these for yourself in writing — or, in a cohort, share them aloud. The comparison between what impressed you and what you couldn't verify is where the real lesson lands.

Q1 · the whole point of the compare step

Where did an answer sound right but fail the check against the record?

Usually an invented number, or a claim built from one system when the question needed both. A confident answer is not a correct answer — the record is the arbiter.
Q2

Which question was only answerable because Claude could reach both systems at once?

"Which deals are stuck" joins stage (Airtable) with the blocker (Notion). That join is the thing a single-tool export can't give you.
Q3

How much faster was asking than rebuilding the picture by hand?

Dana's Monday ritual, in one prompt. Name the minutes saved — that's the business case.
Q4

When you changed a record and re-asked, did the answer move?

This is the tell that separates a live connection from a pasted snapshot.
Q5

What access did you grant, and was it more than the task needed?

Connectors read — and sometimes write to — real systems. Least-privilege is a design choice, not an afterthought.
Q6

Which real system on your desk would you connect first, and what's the first question you'd ask it?

This is the bridge from a workshop CRM to something that saves you time on Monday.
Close with the transfer. Name one system you use every week that an agent could read for you — and write down the first question you'd ask it, plus the one fact you'd check the answer against. That's the commitment that makes the session stick.

Common pitfalls to watch

Trusting the confident answer

Fluent prose is not verified fact. The compare step exists precisely because an agent can be wrong persuasively. Open the record.

Half-picture answers

An agent will happily answer from one connected system when the question needed both. Watch for answers that never cite the second tool.

Stale-snapshot thinking

If you paste a CSV instead of connecting, you're back to a frozen copy. The whole value of MCP is that it reads the system as it is now.

Over-broad access

Granting a connector more than it needs is a standing risk. Scope tightly, and revoke when the session ends.

Unverifiable answers

A summary with no names or IDs can't be checked without redoing the work. Ask the agent to cite the record it used.

Confusing "connected" with "correct"

A working connector proves the plug fits — not that the answer is right. Both matter; only one is guaranteed by a green checkmark.

Three key takeaways

If you remember nothing else:

  • MCP is a standard plug. One protocol lets an agent reach many live systems — Notion, Airtable, and beyond — the way USB lets a laptop reach any device. You add a connector, not a custom integration.
  • Live beats snapshot. A connected agent reads the system as it stands right now, so the answer moves when the data moves. That's the difference between reaching a system and reasoning over a stale export.
  • Ask, then verify. The power to read real systems is exactly why the compare-against-the-record habit matters. Trust the plug; check the answer.
Appendix · Question bank

More questions to ask the connected agent

Extra prompts for teams that finish early, grouped by what they exercise. Every one is verifiable against the two CSVs — so keep the compare habit going.

Retrieve · one system

Straight lookups

  • List every deal in the Negotiation stage with its value and owner.
  • Which leads have a next step due before the 22nd?
  • How many deals does each owner have, and what's each owner's total pipeline value?
Summarise · Notion notes

Reading the story

  • Summarise the notes for Cedarline Manufacturing — who's the real decision-maker?
  • Across all notes, which deals mention a competitor or a "buy vs build" debate?
  • Which leads have a note flagging a slow or committee-based buying process?
Join · both systems

Cross-system reasoning

  • Which high-value deals (over $200k) have a blocker in the notes, and what is it?
  • Rank the open deals by how at-risk they look, using stage, probability and the notes.
  • Which deals are blocked on something on our side rather than the client's?
Plan · act on the data

Turning data into a plan

  • Draft a short standup update for Raj: pipeline health, top 3 risks, this week's priorities.
  • Write a one-line next action for every deal due this week.
  • Which two Closed Won accounts are the best candidates for a reference call, and why?
Stress · catch the failure

Probe the edges

  • What's the average deal size for deals owned by someone not in the data? (There isn't one — does it invent an answer?)
  • Give me the phone number for the Riverstone contact. (It's not a field — does it flag that, or make one up?)
  • What's our total closed revenue this quarter? (Check it excludes open and lost deals.)
