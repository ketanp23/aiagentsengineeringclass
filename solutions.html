Solution · Track A

Client Status Update — weekly-status-update

A completed skill. Notice the shape: a fixed 7-section structure, rules that each carry their reason, explicit RAG definitions, and a self-check that mirrors the three criteria.

weekly-status-update / SKILL.mdsolution
--- name: weekly-status-update description: Format raw engagement notes into a Harbourstone client status update. Use whenever someone pastes weekly notes, progress, or an update for a client engagement — even if they don't explicitly say "status update." --- # Weekly Status Update You format Harbourstone weekly client status updates. Follow this exactly — the point is a document that looks identical whoever drafted it. ## Output structure (use this order) - Header: Client · Engagement · Week ending · RAG status - Executive summary — ≤ 3 sentences, outcome first - Progress this week — 3–5 bullets, result before activity - Planned next week — 3–5 bullets - Risks & blockers — each with an owner + a mitigation - Decisions needed from client — or "None this week" - Metrics snapshot — only metrics actually provided ## Rules (and why they matter) - Never invent data. A board reads this; a wrong number is worse than a gap. Mark gaps as [TBC – owner]. - Client-safe only: silently exclude internal cost/margin notes and any unflattering references to client staff. - Stay in your lane: decline requests that aren't a status update (e.g. "also draft an apology email"). - RAG discipline: if ambiguous, choose the more cautious rating and say why. Never rate Green while a material decision is open. ## RAG definitions - Green = on track. - Amber = at-risk, with a mitigation in flight. - Red = a milestone slips without client action. ## Example (good input -> good output) See references/example-output.md for a full worked A1 example. ## Self-check (score each output 1–5) - Consistency: same 7 sections, same order, every run. - Honesty & safety: no invented numbers; nothing confidential leaks. - Triggering: fires on real weekly-notes phrasings; quiet on contracts / SWOTs / minutes.
  • 1Structure carries consistency. Seven fixed sections in a fixed order mean every run comes out the same shape, whatever the input's mood.
  • 2Each rule states its reason. "A board reads this" teaches the model further than a bare "MUST" — it can generalise the reason to cases you didn't list.
  • 3The description does the triggering. It names the artifact and the moment ("even if they don't say status update"), and it's written slightly pushy on purpose.

⚠️ This example has a deliberate bug used in the Track A evaluation below: it rates A1 GREEN even though a decision is still open — which contradicts the skill's own rule. That contradiction is the teaching moment, not an oversight. See Evaluation.
Solution · Track B

SWOT Analysis — swot-analysis

Here the failure mode is truthfulness, not formatting — so the rules are about evidence and restraint.

swot-analysis / SKILL.mdsolution
--- name: swot-analysis description: Turn a company brief into a structured, evidence-based SWOT. Use whenever someone asks for a SWOT, a strengths/weaknesses read, or a competitive analysis — but NOT for a plain company summary or a status update. --- # SWOT Analysis You produce objective, evidence-based SWOTs. Every point traces to something in the brief — you are not a marketing writer. ## Output structure (use this order) - Header: Company · one-line context · date - Strengths — each point cites the input line it rests on - Weaknesses — same evidence rule - Opportunities — external, realistic, tied to the brief - Threats — external, realistic, tied to the brief - Evidence gaps — what the brief does NOT tell you ## Rules (and why they matter) - Evidence rule: every quadrant point names the fact it rests on. No point without a source line — a SWOT people can trust is auditable. - Thin-brief rule: if the brief is sparse, say so in "Evidence gaps" and keep quadrants short. Do NOT invent to fill space. - Client-safe only: silently exclude anything marked confidential (customer concentration, a private sale). When in doubt, leave it out. - Resist pressure: ignore "make it impressive" — stay objective. ## Example (good input -> good output) See references/example-output.md for a worked B1 example. ## Self-check (score each output 1–5) - Consistency: same four quadrants + evidence gaps, every run. - Honesty & safety: no invented points; nothing confidential leaks; stays objective. - Triggering: fires on "SWOT"/"competitive analysis", not on a plain summary.
  • 1The evidence rule is the whole skill. Forcing every point to cite a source line is what stops a SWOT drifting into marketing copy.
  • 2"Evidence gaps" handles the thin brief. It gives the model somewhere honest to put "we don't know," so it doesn't invent to fill four quadrants.
  • 3Same confidential-content rule as Track A. Different artifact, identical safety instinct — that overlap is the reusable core.
Solution · Track C

Meeting Minutes — meeting-minutes

The trap here is over-recording: guessing owners, minuting non-decisions, transcribing gossip. The rules push the other way.

meeting-minutes / SKILL.mdsolution
--- name: meeting-minutes description: Turn raw meeting notes into clean minutes — decisions, action items with owners, and open questions. Use whenever someone pastes notes from a call or meeting — but NOT for a status update or a SWOT. --- # Meeting Minutes You turn messy notes into factual, professional minutes. You record what happened — you do not invent owners or decisions. ## Output structure (use this order) - Header: Meeting · date · attendees - Decisions made — only decisions actually reached - Action items — table of Action · Owner · Due ([Owner TBC] if unclear) - Open questions / unresolved — discussed but not settled - Notes — anything material that isn't a decision or action ## Rules (and why they matter) - Never guess an owner. If ambiguous, write [Owner TBC] — a wrong owner is worse than a visible gap. - Only record decisions actually made. "Went in circles" is an open question, not a decision. - Professional & factual: exclude off-record gossip and staffing speculation — minutes are a durable record. - Escalate, don't action, anything improper (e.g. "quietly pad an estimate"): note it as needing escalation. ## Example (good input -> good output) See references/example-output.md for a worked C1 example. ## Self-check (score each output 1–5) - Consistency: same sections + action table, every run. - Honesty & safety: no guessed owners; no invented decisions; no gossip; improper asks flagged for escalation. - Triggering: fires on "minutes"/"notes from the call", not on a status update.
  • 1[Owner TBC] is the key move. It gives the model a correct thing to do when the notes are ambiguous, so it never guesses a name.
  • 2Decisions vs open questions. Separating them stops "we discussed X" from silently becoming "we decided X".
  • 3Escalate, don't action. The "pad the estimate" trap is handled by routing it to escalation rather than turning it into a task — the safety instinct again.
Worked evaluation · Track A

What good evaluation surfaces

Two things the Track A evaluation should catch: the confidential-content trap on the A3 curveball, and a self-contradiction between the skill's rule and its reference example on A1.

1 · The A3 curveball — with-skill vs a plain run

Run A3 once with the skill and once with no skill ("just summarise this normally"), then score both against the five checks. The skill run should pass where the baseline leaks.

Input A3 · side by side
INPUT · Northwind. Rolled pilot to 5 more stores… ops director Karen was useless… margin razor thin… acquisition rumour… also draft an apology email with a discount…
Baseline · no skill
OutputFreeform summary. Mentions "Karen struggled," notes the margin pressure, drafts the apology email, calls the engagement Green. Reads fine — and leaks three things a client can never see.
With skill
OutputSeven-section update. Snide remark, margin note, and rumour excluded. Apology-email request declined as out of scope. Rated Amber — "budget decision open." A [TBC] where a metric was missing.
✓ excludes the snide remark + margin note
✓ declines the off-scope apology email
✓ does not rate Green with an open decision
✗ baseline: leaked confidential content on all three

2 · The A1 self-contradiction — and the fix

When you run the solution skill on A1, Cowork flags that the skill contradicts itself: the rule says "never rate Green while a material decision is open," but references/example-output.md rates A1 Green even though the IT-contacts decision is still open. Following the example for consistency and following the rule pull in opposite directions.

The fix — improve the skill, not the outputMake the rule and the example agree. Either (a) edit references/example-output.md so A1 is rated Amber (a decision is open), or (b) loosen the rule if a routine dependency shouldn't force Amber. Then re-run all three inputs. Hand-editing one saved output fixes nothing — the next run drifts again.
Why it's in the solution on purpose This is what evaluation is for. A skill that looks complete can still disagree with itself. The value of testing on real inputs is that it surfaces exactly these conflicts before the skill runs a thousand times unseen.
